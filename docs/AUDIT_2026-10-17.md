# Ponytail audit and macOS review — 17 October 2026

What this repo does: Camera Media Importer is a native macOS utility that scans camera cards and folders, then copies or moves media and sidecars into device/date folders. It can handle duplicate names and eject source devices. The assumed load is one user, one app window, several camera cards, thousands of files, and videos several gigabytes in size.

Reviewed all five app source files, the package manifest, regression checks, README, previous review, and build, icon, and uninstall helpers. Existing uncommitted README, UI, and bundle-script edits were preserved. No third-party packages are declared or linked: there are no package versions or lockfiles to update. Apple framework updates come with macOS and its SDK; no system software was changed.

The initial audit was followed by targeted fixes and verification. The review used the published [build-macos-apps plugin](https://github.com/openai/plugins/tree/main/plugins/build-macos-apps) guidance for SwiftPM, test triage, SwiftUI state ownership, and signing. The plugin was read from its published source, not installed.

## Must fix — addressed

1. **Video comparison retained buffers for the whole file** (`Sources/CameraFileSortSwift/Importer.swift`, `identicalContents`)
   - **What this is:** Import-date deduplication compares earlier imports byte for byte in one-MiB chunks.
   - **Problem:** Foundation's autoreleased read buffers accumulated until the enclosing per-file pool drained. A synthetic 512-MiB video comparison reached 1,093,369,856 bytes of maximum resident memory despite the small chunk size.
   - **Fix:** Drain an autorelease pool after every pair of reads. The identical fixture and optimized harness now peak at 17,448,960 bytes, while still checking all bytes and final metadata. A permanent 512-MiB comparison fixture was added to `check.sh --performance`.
   - **If we skip it:** Reimporting multi-gigabyte videos can consume gigabytes of RAM and cause swapping or termination.

2. **Keep-both could separate RAW/JPEG captures from their sidecar** (`Sources/CameraFileSortSwift/Importer.swift`, `keepBothTargets`)
   - **What this is:** Related files need a common numbered basename so editing software can associate their sidecar metadata.
   - **Problem:** With `E.ARW` already present, importing `E.ARW`, `E.JPG`, and `E.XMP` grouped each primary separately. The RAW received `_1`, while the JPEG and shared sidecar could remain unnumbered. The new regression failed on the original code.
   - **Fix:** Reserve filenames by the source path without its extension, grouping RAW, JPEG, and sidecar together. The regression now verifies that all three receive `_1` and transfer successfully.
   - **If we skip it:** The imported RAW can lose its automatic association with the editing metadata.

## Build environment finding

3. **The default installed SDK cannot compile SwiftUI state**
   - **What this is:** The supported bundle build is `scripts/build_app_bundle.sh`.
   - **Problem:** This Mac's default `MacOSX.sdk` points to macOS 27.0, whose SwiftUI `State` macro needs a compiler plugin absent from the installed Command Line Tools. The plain shell build fails with `SwiftUIMacros.StateMacro` missing. Both direct build backends also failed; this is not a regression from the importer fixes.
   - **Fix:** The same shell script succeeds with the already installed macOS 26.5 SDK, using its existing SDK override below. A matching complete toolchain is needed to use the macOS 27 SDK. The existing script and minimum supported macOS version were not changed by this audit.
   - **If we skip it:** A plain build on this installation fails before packaging. SwiftPM also warns that the script's native build backend is deprecated; a future toolchain migration needs separate verification.

```sh
./scripts/build_app_bundle.sh --sdk /Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk
```

## Security and implementation assessment

The source has no network client, telemetry, downloaded code, or third-party runtime dependencies. Transfers validate folder settings, reject output escape/symlink cases, stage copies before committing them, preserve an existing destination on failed overwrite, and delete a moved source only after committing its destination. Regression checks cover these paths. These controls are appropriate for a local utility running with the user's filesystem permissions.

No additional reproducible security vulnerability was identified in this review. This is not proof that none exists. The importer is not a security boundary against another process with the same user's permissions racing filesystem changes. Source size/modification checks are not a full destination readback or a power-loss durability guarantee. Public distribution still requires Developer ID signing and notarization.

The existing single-window state ownership and serial transfers suit this app. No new dependencies, architecture layers, UI redesign, or speculative refactoring were needed.

Verdict: Two reproducible defects fixed with small changes. Automated filesystem checks and packaging pass with the explicit SDK override; hardware and interactive UI validation remain necessary before a release.

Not checked: Interactive GUI behavior, long-running GUI memory use, Intel hardware, macOS 13 hardware, real camera eject/removal, full-disk and power-loss behavior, network/file-provider interruption, and Developer ID/notarization. No zero-bug or zero-leak guarantee is claimed.

## Follow-up: GUI and simulated hardware failures

The user requested simulated failures only. The following checks extend the initial audit; no physical camera/card was connected or disconnected.

- **GUI import:** Selected a temporary source and destination with the native file pickers. Scanned 1,000 photos, 1,000 sidecars, and one 128-MiB synthetic video. Imported all 2,001 files; independently checked every output against its source using SHA-256. All matched.
- **Import controls:** Observed source, device, destination, scan, settings, and import controls disabled during transfer. Completion showed 2,001 copies and zero failures.
- **Duplicates:** Opened and cancelled the duplicate-policy sheet, verified controls unlocked, then repeated the import and chose Skip. Completion showed 2,001 skips and zero failures.
- **Repeated work:** Completed 60 additional scan actions in the same GUI process without a hang.
- **Device management:** Blank names left Add disabled. Attempting `../escape` displayed the validation error without adding a device. Escape closed the sheet. Tested default-size scrolling and native window zoom/restore.
- **Missing source:** Renamed the disposable selected source folder before scanning. The GUI reported `Cannot scan all files` and the unreadable source path. Restoring the folder allowed successful scans again.
- **Full destination:** Created a disposable 16-MiB HFS+ disk image. The engine's move/overwrite test attempted a 32-MiB file and reached an actual insufficient-space error. The source and old destination survived, and staging was cleaned. The GUI then copied 2,000 small files to the image and reported its 128-MiB video as failed due to insufficient space. The original video remained intact; neither a partial final video nor staging files remained.
- **Denied writes:** Made a temporary destination directory read-only. Move/overwrite failed while preserving the source and old destination, with no staging leftovers. Restored permissions afterward.
- **Source lost between files:** Renamed a temporary source folder immediately after the first successful move. The first file committed, the second failed, and its original survived in the renamed source. Added this and denied-write preservation to the permanent regression suite.
- **Virtual card detached:** Imported two files from the disk image, detaching only that virtual volume after the first copy. The second transfer was reported failed. Remounted it and verified both originals and the failed-overwrite destination remained intact. The disk image was unmounted after testing.

### Live GUI memory

Sampled the actual signed release GUI process (PID 3714) every ten seconds while using file pickers, importing, scanning repeatedly, opening device management, zooming, and idling. The soak began after initial launch and continued across these actions. This process used the pre-status-fix build; the rebuilt status fix was verified separately after the soak.

| Measurement | Result |
| --- | --- |
| Samples / duration | 61 / 600.6 seconds |
| Initial resident memory | 130.25 MiB |
| Peak resident memory | 193.44 MiB |
| Final resident memory | 191.28 MiB |
| Final two idle minutes | 191.27–191.28 MiB; sampled CPU 0% |

Memory rose in steps as different native panels/windows were exercised, rather than continuously with the repeated scans. The final idle plateau is evidence only for this ten-minute workload, not proof against slow leaks. RSS includes resident shared/framework pages; the live leak tool separately reported a final physical footprint of 65.8 MiB and a 100-MiB peak.

Apple's live `leaks` scan did **not** report zero: one scan identified 653 allocations / 29,312 bytes; a later scan identified 1,144 allocations / 46,016 bytes after additional native panels and window actions. A subsequent idle scan showed the same 46,016-byte total. A fresh launch of the rebuilt app (PID 4282), before opening any file pickers, reported 284 allocations / 14,256 bytes. Visible records include Foundation/XPC connection cycles and small arrays. All scans warned that the process was not debuggable and inspection was restricted. Allocation stacks were unavailable, so these findings cannot reliably be assigned to app code or dismissed as framework behavior. The earlier zero-leak regression executable result does not clear these GUI findings. Proper allocation-stack profiling in a debuggable GUI build remains open work before claiming the GUI has no leaks.

Raw local evidence is in `.build/gui-audit-memory.csv`, `.build/gui-audit/live-leaks.txt`, `.build/gui-audit/live-leaks-final.txt`, and `.build/gui-audit/fresh-launch-leaks.txt`; the temporary volume fault harness is retained at `.build/gui-audit/failure-checks.swift`. These generated files are ignored by Git. The original destination and preferences were restored; generated sources were removed from the GUI selection and the disposable volume was unmounted. No physical-media integrity or overnight stability claim follows from these tests.
